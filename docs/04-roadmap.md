# 04 · 路线图、验收与风险

## 1. 版本计划

| 版本 | 周期 | 交付 | 内容量 | 出口条件 |
|---|---|---|---|---|
| v0.0 探针 | 2 周 | 系统能力编排脚本（mac 一键开「朗读所选」+ 图文教程）；10 位老人实测 | 0 | 拿到「用不用」的真实答案 |
| v0.1 | 5 周 | Web 版识字卡 + Electron mac 壳 + 双架构 DMG + 公证 | 50 词 | 陌生老人可无指导完成 T1 |
| v0.2 | 5 周 | 屏幕框选 OCR 朗读（Vision）+ TCC 图文引导 | 50 | 框选到出声 < 1.5s |
| v0.3 | 6 周 | 内容流水线 + 金标准回归 + FSRS 复习 | 300 词 | 回归通过率 ≥ 98% |
| v0.4 | 5 周 | Windows 构建 + WinRT OCR | 300 词 | 双平台功能对齐 |
| v1.0 | 8 周 | 网页阅读器 + 三句话摘要 + 生字本 + 手动更新 | 1000 词 | 留存 5/10 |

**v0.1 只做 macOS 是刻意的。** 人力有限时，一个平台做到能用，好过两个平台都半残。

## 2. v0.0 探针为什么值得做

花两周，可能省掉六个月。具体交付：

1. 一份 `macos-enable-speech.md`：从「系统设置」到「Option+Esc 朗读」的图文步骤，含三张截图；
2. 给 10 位老人装上，教一次，然后**消失两周**；
3. 回收四件事：
   - 他们主动打开了几次？
   - 卡在哪个按钮/对话框？
   - 有没有去用微信/银行 App？
   - 他们抱怨的原话是什么？

**如果两周内 0 人主动使用，说明「教老人用电脑」这个需求被高估了**，应立刻转向纯「识字卡 + 子女辅助」形态，省下的钱以百万计。

## 4. 验收标准

### 4.1 功能验收（自动化）

- 内容：CI 全绿（schema、用字表、长度、图文打分、回归集）
- UI：axe-core 无 critical；对比度 ≥ 7:1；可点区域 ≥ 88×88
- 性能：冷启动 < 2.5s；OCR→出声 < 1.5s；常驻内存 < 250MB
- 安全：无白名单外请求；CSP 生效；`nodeIntegration=false`

### 4.2 可用性验收（必须真人）

10 位 65–80 岁、识字量 < 500 的老人，**无指导测试**（主持人只说「你随便用用」）：

| 任务 | 通过标准 |
|---|---|
| 第一次打开，查一个字的念法 | ≤ 60s，≥ 8/10 人 |
| 听到「再念一遍」并成功重播 | ≥ 9/10 人 |
| 框选朗读一段微信消息 | ≤ 45s，≥ 7/10 人 |
| 连续使用 3 天 | ≥ 5/10 人 |
| SUS 可用性量表 | ≥ 75 |

### 4.3 观察而非询问

老人会说「挺好的」，但行为不会撒谎。重点记录三件事：

1. 第一次看到大按钮时，是**点**还是**犹豫**？
2. 出错后，是**再试**还是**叫子女**？
3. 离开座位时，会不会**关掉软件**？

## 7. 可持续性

1. **双 owner 制**：每个模块至少 2 名 owner，写进 CODEOWNERS。
2. **反馈回路**：GitHub Issue 模板化的「老人反馈表」（子女代填），不做联网埋点。
3. **资金**：申请公益基金会 / 开放科技基金；不接广告、不做内购。
4. **扩展红利**：架构上把「文盲群体」抽象出来，同一引擎可服务少数民族语言使用者、听障者、中文学习者。这决定了能不能吸引志愿者——**意义感比功能重要**。
