# 13 · 个人开发者内容边界（2026-10-27）

> 这份文件是对旧版“内容必须人工审校、必须做老人测试才能发布”条款的修订。
> 字伴目前由个人开发者维护，没有团队、预算和伦理审查资源去完成**人工逐条审校**或**老年人可用性试验**。
> 与其写一条做不到的硬性条款，不如把实际边界写清楚，并保证不冒充做过。

## 1. 修订后的条款

1. **人工审校和老人测试不再是发布/合并的前置条件。**
   个人开发者版本以“机器门禁 + 抽检 + 明确标注 + 可回滚”为实际流程。
2. **内容仍然是实验草稿。**
   字卡和屏幕语料保持 `status: draft` 或机器审校标记；不使用 `human_ok`、`published` 来暗示人工审校。
3. **不得声称做过没有做的事。**
   UI、README、发布说明、Issue 回复都不能写“已人工审校”“老人验证”“专家审过”。
   可以写“机器检查通过”“个人开发者抽检”“欢迎反馈”。
4. **C5 对抗审校、人工复核、老人测试仍然是有价值的工作，但改为可选/社区贡献。**
   谁有条件做，就按 [docs/01](01-ai-content-pipeline.md) 记录审校人和范围；没做就不写。
5. **风险由产品边界承接。**
   医疗/金融/法律词只解释“是什么”，不给建议；风险提示不是专业意见；
   内容可能出错，用户应能以“这句话看不懂/不对”反馈，开发者按反馈修正。
6. **安全、隐私、默认不联网、无广告这些条款不因本修订放宽。**
   本文件只调整内容审校/老人试验，不调整安全红线。

## 2. 为什么改

- 个人开发者无法稳定组织 3–5 位老人做无指导测试，也无法对 500+ 条内容做逐条人工审校；
- 旧条款把所有内容卡在“永远不能发布”，实际结果是文档和现实脱节，或者被迫在发布说明里含糊其辞；
- 更诚实的做法是：**降低宣称，不降低透明度**。内容可以实验性使用，但必须一直带着“未人工审校”的标签。

## 3. 对现有文档的约束

- 本文件优先于以下旧表述：
  - “发布前必须人工审校”；
  - “必须做老人测试”；
  - “未人工审校禁止发布/合并”；
  - “C5 + 人工是发布前置条件”。
- 旧文档中仍保留的“人工审校/老人测试”应理解为**可选建议**，不再是发布阻塞项。
- 如果未来真的完成了一次人工审校或老人测试，应在 [CHANGELOG](../CHANGELOG.md) 和对应内容说明里记录：
  谁、何时、覆盖多少条、发现了什么；不要只写一句“已审校”。

## 4. 对用户/贡献者的说明

- 这是个人维护的实验项目，不是医疗器械、金融建议或政务指南；
- 发现释义/例句不对，请开内容纠错 issue，附上词条和理由；
- 愿意帮忙审校、试用的老师/家属/老人，欢迎自愿参与；不参与也不影响项目继续以实验版运行；
- 任何测试都必须自愿、匿名、不能收集可识别个人信息，也不能录屏/录音。
